Kern Studio · Engineering audit · 7 Oktober 2026

Optimalkan cara agent menyelesaikan task. Uji OMP sebagai engine kedua.

Pi masih cocok untuk fondasi Kern. Dari keluhan lu—agent bilang selesai padahal hasil belum benar, lalu proses lambat atau muter-muter—prioritas pertama adalah verifikasi hasil, kemudian pengurangan kerja berulang. OMP menawarkan tool coding yang menarik, tetapi migrasi perlu adapter dan pengujian kompatibilitas.

Basis: source v0.2.42, HEAD b1ddb4b, CLI Pi lokal 1.0.4, serta dokumentasi resmi Pi dan OMP. OMP belum terpasang di PATH. Audit source, bukan hasil benchmark model atau pengukuran latensi desktop.

Produk yang sebenarnya lu butuhkan

Workspace coding harian harus membuat perubahan yang tepat, bisa diperiksa, bisa dilanjutkan, dan siap diserahkan. Chat, browser, Graphify, Kanban, dan pipeline mendukung hasil itu.

Fondasi tersedia

Kerja terisolasi

Project chat, worktree, session history, fork, steering, checkpoint, dan terminal. Non-git project bekerja langsung di folder; workspace multi-repo memakai overlay dan aktivasi worktree saat menulis.

Fondasi tersedia

Konteks & tool

Skills, Graphify opsional, rekomendasi Jev opsional, API contract tools, auto-format, browser, dan task lookup. Global chat memakai RAG; project chat punya jalur konteks berbeda.

Fondasi tersedia

Review & delivery

Diff review, Kanban, pipeline tersimpan, input commit yang direview user, retry dan bantuan perbaikan pipeline. Deep Research tersedia sebagai sesi terpisah dengan tool terbatas.

Sumber: README.md; ChatView.run / taskContext / sendWithSkill; pi_rpc.spawn_pi_rpc; pipeline.run_pipeline_thread. Ketersediaan fitur belum membuktikan langkah itu selalu dipakai secara tepat oleh agent.

Alur sekarang: eksekusi fleksibel, kualitas masih bergantung agent

  1. Buka chat → cek Graphify bila aktif → siapkan worktree/overlay → spawn Pi beserta extensions.
  2. Pulihkan history dan minta model, command, state, serta statistik sesi. UI memakai beberapa retry berbasis timer saat startup.
  3. Kirim task → baca attachment → tunggu checkpoint best-effort → tambahkan Plan Mode / data Kanban bila sesuai intent → kirim RPC prompt.
  4. Hook Graphify mencari konteks; hook Jev memilih saran tool/skill bila enabled. Model menentukan pembacaan, edit, dan command berikutnya.
  5. Setiap hasil write/edit yang didukung langsung memicu Prettier sinkron.
  6. UI memproses pesan dan tool events. agent_end sudah membuat UI idle; agent_settled juga ditangani.
  7. Pipeline berjalan bila diminta eksplisit, dengan stage, retry, dan proposal commit. Belum ada verifier wajib yang mengaitkan acceptance criteria task dengan hasil akhir project chat.
Bedakan tiga kondisi: model berhenti satu run, runtime benar-benar settled, dan task memenuhi acceptance criteria. Ketiganya perlu state berbeda.

Alur usulan yang proporsional dengan task

Task kecil bisa langsung discovery → edit → focused check. Task kompleks memakai plan. Plan read-only berlaku saat dipilih; deployment/push mengikuti izin user. Jangan membuat setiap task wajib melewati planner dan reviewer LLM terpisah.

Temuan yang layak diperbaiki dulu

Prioritas di bawah adalah penilaian dampak engineering. Potensi perlambatan belum diukur.

P101 · UI terlalu cepat menganggap agent selesai

ChatView.tsx:1758 menangani agent_end dengan status idle, streaming false, dan event UI bernama agent_settled. Pi membedakan run end dari settled: retry, compaction, steering, dan follow-up masih bisa berlanjut. UI bisa menampilkan idle terlalu dini.

Usulan: satu reducer lifecycle yang memisahkan run, retry, queue, settle, cancel, dan process exit. Gunakan agent_settled sebagai batas idle Pi yang final, dengan fallback eksplisit untuk versi lama. Uji trace retry + follow-up + compact, bukan hanya respons normal. Kontrak RPC Pi.

P102 · Akhir task belum punya bukti terstruktur

Jalur akhir agent menutup streaming dan membaca stats, tanpa memverifikasi acceptance criteria, diff terakhir, atau pemeriksaan yang diwajibkan task. Pipeline sudah punya status pass/fail, tetapi opt-in dan terpisah dari penyelesaian chat. Agent tetap bisa menjalankan test atas instruksi sendiri; hasilnya belum menjadi kontrak completion host.

Usulan: task ledger berisi goal, constraints, changed files, checks, unresolved issues, dan outcome. Check merekam command, cwd, exit code, serta hash diff yang diuji. Edit setelah check membuat bukti lama invalid. Sediakan hasil verified / complete with limitations / incomplete; read-only analysis cukup source evidence, bukan wajib build. Gunakan verifier deterministik dulu; review LLM hanya bila kompleksitas membutuhkannya.

ChatView.tsx:1758; pipeline.rs:663; extensions/pipeline-runner.ts:5.

P103 · Checkpoint mengubah history branch kerja

create_checkpoint_in_repo menjalankan git add -A dan git commit pada branch aktif. maybeCreateCheckpoint ditunggu sebelum prompt, termasuk follow-up/steer. Ini menjaga snapshot, tetapi mengubah HEAD/index dan berpotensi mencampur snapshot sementara dengan commit delivery. Saat agent masih aktif, snapshot perlu dikoordinasikan dengan write yang sedang berjalan.

Usulan: simpan snapshot pada refs khusus refs/kern/checkpoints/... dengan temporary index / commit-tree, tanpa memajukan branch atau mengubah staging user. Ikat snapshot ke message ID, tandai jika gagal, dan serialisasi dengan mutation queue. Deduplikasi snapshot bila diff sama.

worktree.rs:861; ChatView.tsx:2612, 3536.

P104 · Plan Mode berupa prompt, belum pembatas eksekusi

PLAN_MODE_PREFIX meminta agent tidak mengedit dan menambahkan marker approval. Jalur normal memakai prefix; sendPrompt dan jalur steer/follow-up tidak menerapkannya. Active tools tetap tersedia. Jadi mode ini bergantung kepatuhan model dan jalur dispatch.

Usulan: mode disimpan di session host dan berlaku pada semua dispatch. Batasi tool mutasi dan command eksekusi dalam mode plan; cukup read/search/inspection. Untuk shell, klasifikasi read-only harus konservatif atau gunakan tool inspeksi terstruktur. Approval mengubah mode host sebelum implementasi.

chat-utils.ts:458; ChatView.tsx:2548, 2594, 3537.

P205 · Formatting setiap edit bisa mengganggu edit berikutnya

auto-format.ts:51 memakai execFileSync; tool_result:64 memformat setiap write/edit. Ini memblokir event loop runtime selama formatter berjalan dan bisa mengubah teks yang masih dipakai model sebagai target edit berikutnya. Hook hanya mengawasi write/edit; perubahan lewat bash tidak lewat formatter ini.

Usulan: antrean touched files per batch/turn, formatter async dengan cancellation dan timeout, memakai konfigurasi/version proyek. Format sebelum verifikasi akhir, lalu baca diff final. Jika format-on-edit dipertahankan, hasil tool harus menjelaskan source terbaru dan koordinasi mutasi per file.

P206 · Graphify mengulang query tanpa task-aware cache

Hook menjalankan query semua graph pada setiap before_agent_start, memakai maksimal 2.000 karakter prompt, budget 1.200 per graph, timeout 30 detik, lalu memotong gabungan ke 12.000 karakter. Query berdasarkan pesan saat ini bisa kurang tepat untuk follow-up singkat. Satu query gagal membuat keseluruhan Promise.all masuk catch; hasil graph lain yang sukses tidak disisipkan. Startup memakai graph lama sambil refresh background.

Usulan: cache per task + graph fingerprint; scope repository relevan; kombinasi goal dan pesan terbaru; allSettled untuk partial results; provenance dan freshness eksplisit; truncation diberi tanda. Graph untuk hubungan kode, LSP untuk simbol/source terkini, pencarian teks untuk literal/config. Path translation harus mempertimbangkan repository overlay, bukan hanya string replacement.

graphify-context.ts:12–66; ChatView.run:2220.

P207 · Jev masih rekomendasi awal, bukan workflow supervisor

Jev Off secara default; Shadow/Advisory memberi maksimal satu tool dan satu skill berdasarkan prompt saat ini. Kandidat dibatasi 48 per jenis menurut urutan katalog. Routing belum membawa goal sesi / current phase / hasil kegagalan, dan kandidat setelah batas tetap tersedia tetapi tidak dinilai. Helper frontend recommendSkills tidak ditemukan call site di source aplikasi. File ranking, rule compliance, dan compaction Jev masih backlog.

Usulan: ukur utility rekomendasi pada corpus task Indonesia/English; beri state task terbatas; shortlist relevan sebelum batas kandidat. Routing harus bisa memilih none atau beberapa capability bila dibutuhkan. Pertahankan fallback, jangan tambah provider call setiap langkah tanpa bukti manfaat.

jev-routing.ts:23, 89, 137; skill-recommendations.ts:49; docs/plans/2026-10-02-001-feat-jev-agent-workflows-plan.md.

P208 · Memory lintas sesi terikat folder sementara

Prompt meminta durable learnings pada <worktree>/memory.md. File ini ignored, dibuat ulang dari template bila tidak ada. Worktree bersih tanpa commit ahead bisa dihapus paksa walau memory berisi. Pi history tetap durable; file memory lokal itu sendiri tidak dijaga oleh jalur cleanup ini.

Usulan: simpan project memory dan task ledger di direktori durable milik app, dipisahkan per repository/task. Sertakan sumber dan timestamp, hindari mencampur preferensi user dengan kesimpulan source yang bisa basi. Worktree boleh menjadi view/symlink, bukan satu-satunya salinan.

pi_rpc.rs:452; worktree.rs:178, 420.

P209 · Dependensi worktree perlu keputusan otomatis

Prompt sudah mendokumentasikan node_modules symlink dapat gagal di Turbopack, lalu meminta agent mengganti symlink dengan install lokal setelah kegagalan. Ini recovery yang berguna, tetapi task berulang bisa mengulang diagnosis/install yang sama.

Usulan: profil proyek menentukan dependency strategy berdasarkan package manager, lockfile, build system, dan perubahan dependencies. Shared read-only dependency hanya untuk kondisi yang kompatibel; local install saat lockfile berbeda. Tampilkan environment readiness sebelum build.

pi_rpc.rs:452; worktree.create_worktree.

P210 · Runtime contract dan orchestration tersebar

spawn_pi_rpc menggabungkan lifecycle, context, extension, environment, tool allowlist, browser bridge, dan repair. ChatView juga memuat startup, dispatch, event mapping, pipeline coordination, serta rendering. Installer mengikuti upstream moving script; belum terlihat compatibility gate berdasarkan versi yang didukung pada jalur spawn.

Usulan: satu RuntimeAdapter, registry capabilities, dan event reducer. Simpan versi engine yang diuji; cek versi/protocol saat startup, smoke-test upgrade sebelum switch, dan pertahankan rollback. Pecah module mengikuti behavior, bukan refactor besar tanpa kebutuhan.

pi_rpc.rs:266, 572; ChatView.tsx:322, 2134.

Pi, OMP, atau pendekatan lain?

Rekomendasi sekarang

Pi + perbaikan Kern

RPC cocok dengan host Rust/Tauri. Extension, active tool control, MCP, dan lifecycle hook sudah mendukung perbaikan workflow tanpa fork runtime.

Biaya: Kern tetap membangun ledger, verification, environment setup, dan memory sendiri. Pi extensions.

Eksperimen terukur

OMP sebagai opsi

Hashline edit, AST tools, LSP navigation/rename/diagnostics, subagents, serta plan/goal tools menarik untuk refactor dan task kompleks.

Biaya: adapter events, extension porting, session/auth store, tool result UI, dan potensi capability overlap. Keunggulan pada task lu belum terukur. OMP capabilities.

Jika kebutuhan berubah

Pi SDK / ACP

Pi SDK bisa menjadi pilihan bila orchestration dipindah ke sidecar TypeScript. ACP relevan bila Kern ingin host beberapa agent/editor lewat protokol umum.

Biaya: lapisan proses/protokol tambahan; perlu cek coverage checkpoint, tree, compaction, dan custom tool. Untuk host Rust sekarang, RPC sudah sesuai. Pilihan integrasi Pi.

OMP feasible, tetapi bukan penggantian nama binary

Urutan implementasi yang gua pilih

  1. Correctness dulu: lifecycle reducer, task outcome + check evidence, Plan Mode di host, checkpoint tanpa memajukan HEAD. Ini memperbaiki Pi maupun OMP.
  2. Kurangi kerja berulang: batching formatter, context cache + freshness, dependency readiness, durable memory dan resume ledger.
  3. RuntimeAdapter: contract start/resume/prompt/steer/abort/events/capabilities dengan test fixture Pi. Baru tambahkan adapter OMP eksperimental; jangan rewrite UI.
  4. Bandingkan task nyata: Pi sekarang, Pi setelah perbaikan, dan OMP pada workflow Kern yang sama. Aktifkan OMP per project/task setelah ada hasil yang konsisten.

Tanpa telemetry, estimasi persen percepatan atau klaim engine terbaik akan spekulatif. Prioritas bisa disesuaikan dengan frekuensi kegagalan yang lu alami.

Ukuran optimal: lebih sedikit koreksi user, hasil lebih dapat dipercaya

Mulai dengan 20–30 task representatif: bugfix, fitur kecil, refactor lintas file, Next build di worktree, perubahan multi-repo, plan read-only, retry provider, compact/resume, dan review tanpa edit. Gunakan repository snapshot terisolasi, model utama yang sama, prompt dan acceptance criteria yang sama. Pin versi engines, katalog tools, settings, serta budget; ulangi beberapa run untuk mengurangi variasi model.

Hasil

Acceptance pass rate, false completion, jumlah koreksi user, regression, scope drift, dan constraint retention sesudah resume.

Proses

Waktu sampai task verified, p50/p95 startup dan pre-model hooks, edit rejection, repeated search/read, retry/failure rate.

Biaya

Token dan biaya semua calls termasuk Jev / advisor / subagent. Ukur waktu review dan setup runtime, bukan hanya durasi model.

Target engineering awal: read-only plan tidak memutasi file; checkpoint tidak mengubah HEAD/index; idle hanya saat runtime settled; bukti check sesuai diff terakhir; resume tetap menyimpan goal dan constraints. Target kemenangan OMP ditentukan setelah baseline, bukan angka universal.

Audit read-only terhadap implementasi aplikasi; tidak memasang OMP, tidak mengirim request model/provider berbayar, dan tidak mengubah runtime. Graphify update/query dijalankan sebagai gate discovery; update melaporkan topology unchanged. Artifact menggunakan token OpenDots dan tipografi native dari src/opendots.css, stylesheet yang mendapat prioritas terakhir di App.tsx. Tampilan ini adalah laporan engineering, bukan screenshot UI aplikasi.
